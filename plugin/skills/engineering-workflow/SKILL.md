# Engineering Workflow

Используйте этот рабочий цикл для нетривиальных задач разработки, рефакторинга и исправления ошибок.

## 1. Ориентация по фактам (Orient)

1. Проверьте состояние дерева (`git status --short`, текущую ветку, наличие незакоммиченных правок пользователя).
2. При старте работы в проекте проверьте накопленные знания (`carbon_memory.py recall --query "<тема>"`) и открытые чипы (`chip_handoff.py status`).
3. Находите точки входа и определения через `code_search.py symbols` и `code_search.py grep`, читая целевые диапазоны строк (`read_file` со `StartLine`/`EndLine`) вместо загрузки целых модулей в контекст.

## 2. Пропорциональное планирование (Scope)

- **`NO_CHANGE` / малая правка (`<= 3` строк в одном файле):** переходите сразу к точечной проверке и решению без лишних субагентов и без создания worktree.
- **`STANDARD` / многофайловая задача:** зафиксируйте затронутые контракты, вызывающий код и решающие тесты до редактирования.
- **`HIGH` / `XHIGH` (безопасность, схемы БД, миграции, CI/CD, runtime-хуки, публичные API):** явно перечислите инварианты отказа, обратную совместимость и план независимого ревью.
- Создавайте отдельный git worktree (`chip_handoff.py open`) только тогда, когда требуется параллельная изоляция от грязного основного дерева или передача независимой подзадачи в отдельную сессию.

## 3. Реализация (Execute)

- Устраняйте первопричину (см. `root-cause-engineering`), а не симптомы.
- Один исполнитель владеет файлом в конкретный момент времени.
- Не затирайте пользовательские изменения в соседних хунках или файлах.

## 4. Верификация и закрытие (Verify & Close)

- Запустите реальные тесты, сборку и проверки типов для затронутой функциональности.
- Для немалых `STANDARD` и всех `HIGH`/`XHIGH` правок выполните проход `simplify-reviewer`.
- Для `HIGH`/`XHIGH` получите свежий `VERDICT: APPROVED` через `/adversarial-review` после финальной правки.
- Завершите ответ точной квитанцией `[gate]` согласно навыку `development-verification`.
